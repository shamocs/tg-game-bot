## 📋 Задача 2 — Сессии и машина состояний (FSM) 🚧

Сейчас `CommandHandler` реагирует только на команды и сразу забывает о пользователе. Бот не умеет «запоминать», что игрок находится в процессе партии, где следующее его сообщение — это игровой ход, а не новая команда.

Нужно реализовать:

- Слой сессий: хранение состояния каждого пользователя (`IDLE` / `CHOOSING_GAME` / `WAITING_FOR_MOVE` / `GAME_OVER`).
- Машину состояний: переходы между состояниями с логированием.
- Роутинг сообщений: если у пользователя есть активная сессия и сообщение не является командой — это игровой ход, а не команда.
- Таймаут сессии: 30 минут неактивности — автоматический возврат в `IDLE`.
- Команду `/cancel` — принудительный выход из игры.
- Стартовое взаимодействие: команда `/play` создаёт сессию, переводит бота в `WAITING_FOR_MOVE` и сразу отправляет пользователю первый запрос хода.

**Сквозное требование:** после `/play` бот сразу ждёт ход. Пока пользователь не ответил — следующий шаг не наступает.

## 📋 Задача 3 — Карточная механика и первая игра 📅

В `Texts.java` заявлены «Классические карточные игры», но игровой логики пока нет. Опираясь на сессии из Задачи 2, нужно реализовать полноценный игровой цикл.

Нужно реализовать:

- Модель `Card` и `Deck`: масти, ранги, тасовка, раздача.
- Правила игры: раунды/уровни, рука игрока, ходы, условие победы, начисление очков.
- Обработку хода: парсинг ответа пользователя, применение к игре, возврат следующего запроса.
- Тексты в `Texts.java`: начало уровня, варианты хода, результат, продолжение, конец игры.
- Кнопки (inline-клавиатура) для действий игрока.
- Обработку некорректного ввода: если пользователь пишет не то — повторный запрос хода, состояние остаётся `WAITING_FOR_MOVE`.

**Сквозное требование:** каждый новый уровень начинается с запроса к пользователю и заканчивается его ответом. Без ответа переход невозможен.

## 📋 Задача 4 — База данных: персистентность и таблица лидеров 📅

При перезапуске приложения через `Main.java` все достижения игроков и статистика побед стираются из оперативной памяти. Требуется долговременное хранение.

Нужно реализовать:

- Подключение БД (SQLite/H2): создание таблиц `players`, `sessions`, `level_results`, `leaderboard`.
- `PlayerRepository`: загрузка/сохранение игрока, сохранение результата после каждого уровня.
- Восстановление сессии при старте: загрузка сохранённого прогресса и предложение продолжить.
- Таблицу лидеров и команду `/top`.
- Сохранение после каждого уровня — не только при выходе.

**Сквозное требование:** каждый уровень — это точка сохранения. После перезапуска прогресс и лидерборд не теряются.

## 📋 Задача 5 — Дополнительные взаимодействия 📅

Развитие бота: больше способов взаимодействия с пользователем на каждом новом уровне.

Идеи:

- Выбор игры перед стартом партии (команда `/play` с меню игр).
- Ежедневные задания и награды за серию побед.
- Внутриигровые подсказки и обучающий режим для новых игроков.
- Достижения и бейджи, отображаемые в профиле.
- Профиль игрока: команда `/profile` со статистикой из БД.
- Мультиплеер — партия с другим пользователем через бота.

**Сквозное требование:** каждое новое взаимодействие — это запрос к пользователю и ожидание его ответа, встроенное в существующую FSM.

## 📐 Сквозное требование ко всем задачам

Игровой процесс строится так, чтобы каждый новый уровень (раунд) начинался с запроса к пользователю и заканчивался его ответом. Бот не переходит к следующему этапу без интерактивного действия игрока.

Связка задач:

- Задача 2 создаёт стартовое взаимодействие.
- Задача 3 поддерживает его на каждом уровне.
- Задача 4 сохраняет результат этого взаимодействия.
- Задача 5 расширяет набор взаимодействий.

## ✅ Критерии готовности проекта

- `/play` запускает игру и сразу просит действие.
- Каждый уровень — запрос + ожидание ответа (без ответа шаг не наступает).
- Результат каждого уровня сохраняется в БД.
- После перезапуска прогресс и лидерборд не теряются.
- `/top` показывает актуальную таблицу лидеров.
